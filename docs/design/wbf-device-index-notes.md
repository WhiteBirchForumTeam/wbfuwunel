## 0. 起點

維護者 2026-09-16 的思路：

1. **Matrix 只規定結果，不規定怎麼算**，規格沒有保證任何實作的效率。
2. 現在「誰跟誰有共同加密房」這套底層，維護者不滿意，想從底層換掉。
3. **兩條路**：HTTP 照 Matrix 那套（給一般 client）；WS 是維護者自己的 client 專用，可以走特規，**讓 server 減重**。前提是結果正確。

## 1. 結論先講

- **只有「發」需要知道別人有哪些裝置**；「收」不需要（§3）。
- **成員變動不需要任何新東西**：它就是房間事件，已經被記錄、被廣播、有補窗（§4）。
- **server 唯一非給不可的是「某人的裝置變了」**，而且上游已經有這份紀錄（§5）。
- 成員、交集、`left`、每房發給過誰、何時換房間金鑰 —— **全部可以在 client 本地做**（§6）。
- ✅ **維護者 2026-09-17 定案七條**（§7）：成員清單帶每個成員的版本號；裝置變動時帳號的版本號必須變；換金鑰、交叉簽章金鑰、簽章都算；client 用 `IdentityBasedStrategy`；房間版本號＋送出時比對，對不上回 `1506 RoomDevicesChanged`、client 自動重試，沒有約定的不擋。§9 是目前的設計結論草稿。

## 2. 走過的路（考慮過、不做，理由留著）

| 想法 | 為什麼不做 |
|---|---|
| **成對表**：`(A, B) → 共有幾個加密房` | 「A、B 有共同加密房」是使用者與房間這張二分圖上的「距離 2」，成對表等於把圖平方後存起來：一個 1000 人房間是 50 萬條關係，有人進出就改一大片。**存一個推得出來的東西，代價卻是平方級。** |
| **只含加密房的成員索引** | 讓交集變短，但仍是在回答一個「不必問」的問題（§6）。 |
| **每個加密房存一個裝置版本號** | 那是把推得出來的東西又快取一次：要維護、要 migration、要重建指令，而且會跟事實對不上。 |
| **把成員變動也寫進逐房的變動列** | 那是**寫入時扇出**：一個事實寫 N 份（N 是他的房間數），寫了就永遠躺著。上游的金鑰變動就是這樣做的（`mark_device_key_update` 對每個房間寫一列），我們不該照抄到成員變動上。 |
| **全域的變動日誌**（一次變動一列，讀的人自己過濾） | 比扇出輕，但成員變動本來就在房間事件裡，根本不需要日誌；裝置變動則上游已經有每人的紀錄（§5）。多一條日誌就是多一個會長大的東西。 |
| **server 持續替每個 client 追蹤** | 那是 Matrix `/sync` 的選擇，不是 E2EE 的必要條件（§3）。 |

⭐ 這幾條的共同錯誤：**被 Matrix 的訊號形狀帶著走**。`device_lists.changed` 是「一串使用者」，於是底層一路被逼去回答「誰跟誰同房」；問題本身並不需要那個答案。

## 3. 收與發不對稱

| | 需要知道別人有哪些裝置嗎？ | 需要什麼 |
|---|---|---|
| **收**（解開別人的訊息） | **不需要** | 對方把那一輪的房間金鑰發給了**我這台裝置**：來源是我自己的 to-device 佇列、金鑰備份、或向我自己的其他裝置要。全是「我自己的東西」。 |
| **發**（我送加密訊息） | **需要** | 送出前，這一輪的房間金鑰必須已經發給房裡每個人的每台裝置。 |

📎 收的一邊唯一碰到別人裝置的，是顯示「這則訊息來自已驗證的裝置嗎」—— 看到陌生裝置時再查、查完快取，是顯示用的，不是解密用的。

**所以追蹤裝置只在兩個時機有意義**：

| 時機 | client 做什麼 | 碰到別人的裝置嗎 |
|---|---|---|
| 啟動、補歷史 | 拉自己的 to-device 佇列（收金鑰），需要時從備份補 | **不碰** |
| **點進房間（前景）** | **先問一次：這房有沒有人換過裝置、要不要重抓**；順便把房間金鑰發到位（暖機） | 只碰這個房間 |
| **按下送出** | 確認這房的成員與裝置是最新的，不是就補發，再送 | 只碰這個房間 |
| 關掉房間 | 不做事 | 不碰 |

另一種「發」是被動的：我自己的新裝置來要舊訊息的金鑰（`m.room_key_request`），只需要知道**我自己的**裝置清單。

**離線時追蹤別人的裝置沒有任何用處**；server 不必替任何人持續追蹤任何東西。

## 4. 成員變動：已經有了

`m.room.member` 是房間事件。`append_pdu` 把**每一個**新事件推給房間的訂閱者（`service/rooms/timeline/append.rs` 的推送），所以成員變動已經：

- **被記錄**：房間時間線上的一則 PDU，帶 `g_seq`（全域）與 `r_seq`（每房）。
- **被廣播**：房間的訂閱者立刻收到。
- **有補窗**：斷線重連用 `Recent`＋`gap`。

跟著房間走的 client，收到成員事件的那一刻就知道「這房的人變了」，不需要 server 再用別的頻道說一次。房間的水位（`r_seq`／`g_seq`）**完全適用於成員變動**。

## 5. 裝置變動：唯一要 server 提供的

「某人換了裝置」**不是房間事件**，不在任何房間的時間線上，房間水位看不到它，client 本地也推不出來。這是唯一轉嫁不到 client 的東西。

現在資料庫裡已經有的：

| 東西 | 存在？ | 形狀 |
|---|---|---|
| 當前的金鑰（每人每台裝置、交叉簽章金鑰） | ✅ | `keyid_key` |
| **每個人的金鑰變動紀錄** | ✅ | `keychangeid_userid` 以 `(使用者, 位置)` 為鍵，`keys_changed` 讀的就是它 |
| 每個房間的金鑰變動副本 | ✅ | **同一張表**另以 `(房間, 位置)` 為鍵 —— 逐房扇出。還有別的讀者：`/sync` 與聯邦（`sending/sender.rs` 組 `m.device_list_update` 時逐房掃它），所以**不能刪，只是通道不碰它** |
| 每人一個版本計數器 | 🤔 半個 | `userid_devicelistversion` 存在，但只有刪裝置那條路會遞增 |

- 號碼：金鑰變動的位置取自 `globals.next_count()`，**跟 `g_seq`、`cd_seq` 同一個計數器**，可以比先後；但它不是事件，傳遞跟房間事件分開。
- ⚠️ 計數器是兩階段的：位置順序 ≠ 看得到的順序（500 可能比 501 晚寫完）。任何「我看到位置 P 了」都要定義成「server 已提交到 P」，不是「我收到的最大號碼」—— (B) 實作 `dl_seq` 時踩過。

## 6. client 本地的兩張表

**全域表：跟哪些 (帳號, 裝置) 建過 1:1 通道**

- **保留，不因為沒有房間交集就刪**。1:1 通道（Olm session）不授予任何讀取權，只是「能加密傳東西給這台裝置」的管線；之後再同房、驗證裝置、轉發金鑰都用得上，不必再搶對方的一次性金鑰。
- 要修剪就依「多久沒用」，不依「有沒有交集」。

**房間表：這一輪的房間金鑰已經發給哪些裝置**

- 某人（例：`weil`）退房 → 從這個房間的表清掉他所有裝置；全域表不動。
- 🚨 **光清表不夠，一定要換一把新的房間金鑰。** Megolm 的房間金鑰可以往前推：weil 手上已有現在這一把，只要不換，他就算不在名單上也解得開之後用同一把加密的訊息。**清表是「不再發給他」，換金鑰才是「他讀不到之後的」。**

**跟傳統 client 的差別**：`matrix-sdk-crypto`（client repo 的 `vendor/`）內部**已經有這兩張表**：

| 這份的設計 | SDK 內部 |
|---|---|
| 全域：建過通道的裝置 | 裝置清單與 Olm session 永久存在本地 |
| 房間：發過金鑰給哪些裝置 | 每個房間的發送金鑰帶一份 `shared_with_set` |
| 有人退房就換金鑰 | `share_room_key(room, users, …)` 的**成員名單是 client 傳進去的**；名單少了誰就自動換鑰（`share_strategy.rs` 註解：「1. Any user left the room」） |

**真正的差別只有一個：誰告訴 client「某人的裝置過期了」。** 傳統是 server 持續算 `device_lists` 推給它（client 維護全域的「追蹤中的人」）；這裡是**點進房間或送出時，只問這個房間的成員**。

接 SDK 的方法：server 回的「換過裝置的人」當成 `device_lists.changed` 餵進去；第一次出現的成員用 `update_tracked_users` 登記。

## 7. ✅ 維護者 2026-09-17 定案

> **1. 提供成員清單時，必須包括每個成員的版本號**（代表他的裝置有沒有變動）。
> **2. 裝置變動時，帳號本身的版本號必須變。** 形狀可以是「序號＋所有裝置 ID 清單的雜湊」，例：`2-abcdef1234`。
> **3. 「裝置變動」包含同一台裝置換金鑰，以及交叉簽章金鑰變動**：這兩種都要讓版本號變。（維護者 2026-09-17，回答 §8.2）
> **4. 簽章也讓版本號變，照上游**：不論是自己簽自己的裝置，還是簽別人（驗證），都讓**被簽的那個人**的版本號變。（維護者 2026-09-17，§8.2 的 (a)）
> **5. 客製 client 用 `IdentityBasedStrategy` 發房間金鑰**：只發給被擁有者自己簽過的裝置。（維護者 2026-09-17）
> **6. 房間版本號＋送出時比對**（維護者 2026-09-17 提的方案）：server 把「房間成員 → 各自的裝置版本號」算成**一個房間版本號**，跟成員清單一起發出；client 送加密訊息時帶上它；對不上就拒收，client **自動重試**（拉最新成員清單、比出誰變了、只重查那幾人、補發房間金鑰、帶新號碼重送），不需要人為操作。**沒有帶號碼的 client（HTTP、一般 client）不擋**—— 沒有約定就沒有檢查（宣告過約定的連線漏帶則要擋，§9.5 第 3 條）。
> **7. 錯誤碼 `1506 RoomDevicesChanged`**：1500 狀態家族。訊息帶的房間版本號跟房間成員目前的裝置版本號對不上；額外欄位 `room_version`（目前的號碼）；怎麼重試由 client 決定（§9.5 第 4 條）。（維護者 2026-09-17 同意號碼與名字。實作時在 wire-format §3.4 的表上加這一列。）
> **8. 每個人的版本號是「序號-雜湊」一條變動鏈**：寫進資料庫，一人一列；沒有就當下算，從 `1-雜湊` 開始，之後每次變動 `2-…`、`3-…`。序號看得出這個人的裝置變動了幾次。雜湊的內容由實作決定（維護者的方向：裝置 ID＋簽名集合）；雜湊只屬於這個人。覺得雜湊多餘也可以拿掉，只留序號。（維護者 2026-09-17）
> **9. 房間版本號用全域位置，不用雜湊**。（維護者 2026-09-17）
> **10. 被邀請但還沒加入的人不算**：不在成員清單裡，不進房間版本號，也不發房間金鑰給他。（維護者 2026-09-17）

**第 8–10 條展開（雜湊內容由實作決定，以下是這份筆記的決定）**：

- **每人一列存什麼**：`{序號, 雜湊, 最後變動的全域位置}`。每次經過 `mark_device_key_update` 序號 +1、重算雜湊、記下那次的位置。⏳ 當下才算出來的那一列，「最後變動的位置」要用什麼值（用「現在」會讓房間版本號多跳一次，最壞少數 client 多被 `1506` 一次，是安全側）。
- 📎 **序號數的是「裝置集合的變動次數」，不只是換裝置**：照第 3–4 條，換金鑰、交叉簽章、簽章都會 +1。
- **雜湊只放任何人都看得到的東西**，否則別的 client 算不出同一個值、就失去核對的用途：
  | 放進去 | 不放 | 為什麼不放 |
  |---|---|---|
  | 每台裝置的公開金鑰，含**擁有者自己簽的**簽章，依裝置 ID 排序 | **別人**簽的簽章（例：Alice 驗證 Bob 時留在 Bob 主金鑰上的那筆） | Matrix 只把那筆簽章給簽的人自己看，Carol 查 Bob 時看不到，算出來會跟 server 不同 |
  | 主金鑰、自簽金鑰，含擁有者自己的簽章 | 使用者簽章金鑰（user-signing key） | 只回給本人看 |
  - 演算法：規範化 JSON → SHA-256 → 取前 10 個十六進位字元（例 `3-abcdef1234`）。正確性靠序號，雜湊只用來核對，40 bit 碰撞不影響安全。
  - 別人的簽章不進雜湊，但**序號照樣 +1**（第 4 條），所以「Alice 驗證了 Bob」仍會讓 Bob 的版本號變。
- **房間版本號的公式**：
  > 房間版本號 ＝ max(房間**目前狀態**裡所有成員事件的 `g_seq`, 目前成員各自「最後變動的全域位置」)
  - 有人換裝置 → 他的位置變大；有人加入或離開 → 新的成員事件 `g_seq` 更大。有人離開時他的位置不再算，但他那則離開事件一定更新，所以最大值不會變小。
  - 🚨 **房間版本號必須只增不減**，所以成員事件的 `g_seq` 要從**房間目前的狀態**讀（離開事件會一直留在狀態裡），**不能從 `state_cache` 的成員計數索引讀**：`forget` 會刪掉離開那一列，最大值會掉回去。漏洞長這樣：Weil 離開（V1 → V2）→ Weil forget（掉回 V1）→ 一個還停在 V1、不知道 Weil 已離開的 client 送出，**比對通過**，它的名單裡還有 Weil，**把新的房間金鑰發給了已經離開的人**。
- **被邀請的人不算的後果**（第 10 條）：他加入之前送出的訊息，他加入後解不開，除非之後從別人轉發金鑰或從備份拿。這跟 Element 在「加入後才看得到歷史」的房間行為一致。

🗑 **考慮過、不做：UI 手動補發金鑰**（點訊息 → 選人 → 選裝置 → 發送解密金鑰；或手動刷新房間狀態）。維護者自己否決：這會變成讓 UI 扛正確性的責任。

📎 **傳統路徑（`/sync`＋SDK 持續追蹤）的正確性**：平常可靠，但不是萬無一失 —— 推播鏈掉一環會靜默漏，「查完金鑰到送出」之間對方加裝置也會漏；Matrix 靠新裝置事後要金鑰、金鑰備份補救。我們 HTTP 那條的正確性跟上游同一個水準。

📎 第 3 條的後果：這兩種變動裝置 ID 清單不變、雜湊也不變，所以**版本號要變就得靠序號那一半**。這樣一來，判斷「有沒有變」靠的是序號；雜湊的角色要在細節文件裡重新定（§8.3）。

合起來的效果：client 手上有「我上次看到的每個成員的版本號」，點進房間時拿成員清單一比，**不一樣的就是要重抓的人**；server 不必替 client 算任何交集或差異。

## 8. 下一份細節文件要回答的

1. ~~**版本號的「序號」**~~ ✅ 已定（§7 第 8–9 條）：每人自己的序號＋記下全域位置；房間版本號用全域位置。原題：每人自己的小計數器（例中的 `2`），還是全域位置（跟 `g_seq` 同空間、可比先後）？`userid_devicelistversion` 現在只在刪裝置時遞增，要補到每一條裝置變動路徑上。
2. ~~**「裝置變動」的範圍**~~ ✅ 已定（§7 第 3 條）：換金鑰與交叉簽章都算。還沒定的子題：
   - ~~**簽章算不算**~~ ✅ 已定（§7 第 4 條，(a)）。判準是維護者問的那句：**這個簽章會不會影響房間金鑰的傳遞？** client 的 `matrix-sdk-crypto` 發金鑰有四種策略（`share_strategy.rs` 的 `CollectStrategy`）：`AllDevices` 不看簽章（SDK 預設，MSC4153 不建議）、`ErrorOnVerifiedUserProblem`、**`IdentityBasedStrategy` 只發給被擁有者自己簽過的裝置**（MSC4153 推薦）、`OnlyTrustedDevices` 只發給我信任的。所以：
     - **自簽**（Bob 的自簽金鑰簽 Bob 的新手機）：在 `IdentityBasedStrategy` 下決定新手機拿不拿得到房間金鑰 → **一定要讓 Bob 的版本號變**，否則新手機永遠被跳過。
     - **簽別人**（Alice 驗證 Bob）：只影響 Alice 自己的發送決定（在 `OnlyTrustedDevices` 等策略下），不影響其他人。選 **(a) 照上游讓 Bob 的版本號變**：所有人重查 Bob 一次，簡單且一定正確；(b)「只動 Alice 自己的版本號」較省，留作之後的優化。
     - 結果：會呼叫 `mark_device_key_update` 的五條路徑**全部**要讓版本號變，沒有例外。
   - 序號掛在哪裡遞增：現有會呼叫 `mark_device_key_update` 的路徑是上傳 device keys、上傳交叉簽章金鑰、上傳簽章、刪裝置、聯邦來的 `m.device_list_update`（`users/keys.rs`、`users/device.rs`、`api/server/send.rs`）—— 正好就是「要讓版本號變」的那一組，掛在同一個函式裡就不會漏路徑。
3. ~~**雜湊**~~ ✅ 已定（§7 第 8 條展開）。原題：用什麼演算法、取幾個字元、清單怎麼排序後再算。⚠️ 第 3 條定了之後，「變沒變」靠序號，所以要重新問雜湊為什麼存在：讓 client 拿本地的裝置清單自己算一遍、核對「我手上的清單跟 server 的一致」？若是，要不要把金鑰指紋（不只裝置 ID）也算進去？還是乾脆只留序號？
4. ~~**成員清單從哪條路給**~~ ✅ 維護者 2026-09-17：**沿用現成的成員 API**（`GET /rooms/{room_id}/members`，橋的 `0x13 0x29 Members`），每個人加一個欄位。細節：
   - ✅ **一律帶，不另設開關**（維護者：官方 client 多拿一個值也無所謂）。Matrix client 忽略不認得的欄位，正確性不受影響；成本是每次呼叫多讀每個成員一列版本號，而這支 API 本來就讀整份房間狀態，量級相同。📎 草稿原本提「加 query 變數、要求了才帶」，已拿掉。
   - ✅ **欄位放哪**：每則成員事件的 `unsigned` 裡放這個人的版本號（例 `org.wbftw.device_version: "3-abcdef1234"`），回應最外層放房間版本號（例 `org.wbftw.room_version`）。命名空間字首。
   - **這支 API 本來就讀「房間目前的完整狀態」**（`membership/members.rs`：`room_state_full` 裡的成員事件），正好是房間版本號公式要的來源（只增不減的那一份），算房間版本號是**同一次讀取順手取最大值**。
   - ✅ **清單變了就刷新，是約定**（維護者）：不必另外區分「為什麼變」。⚠️ 但要注意一個事實：這支 API **什麼參數都不帶時，Matrix 的語意是回房間狀態裡「所有」成員事件**（加入、離開、被踢、被邀請、封鎖都有），上游也照這樣做 —— 不是只有已加入的人。所以二選一，⏳ 待維護者定：
     - (a) **不改預設**：客製 client 帶 `membership=join`（橋的表本來就接受這個變數），或拿到全部之後自己只看 `join`。版本號欄位只加在已加入的人身上；房間版本號照公式，**離開事件的 `g_seq` 仍要算進去**（只增不減靠它）。
     - (b) **把預設改成只回已加入的人**：客製 client 什麼都不帶就拿到想要的，但這是**破壞 Matrix 相容**（官方 client 預期拿到全部），要標 [BREAKING]。
     建議 (a)：客製 client 多帶一個參數，換官方 client 不受影響。
   - 🧹 **`at` 清掉**（維護者：無意義的東西清理掉）：上游忽略 `at`（程式註解 `TODO: at a specific point in time`），client 帶了也沒作用，卻讓人以為有。實作 F2 時從橋的表拿掉（`bridge.rs` 的 `Members` 那一列、`bridge-specs/index.md`、`0x13-room.md`），之後通道上帶 `at` 會被橋回 `InvalidRequest`，不再默默忽略。HTTP 那條是 ruma 的型別，不動。
5. ~~**被邀請的人**~~ ✅ 不算（§7 第 10 條）。原題：依房間的歷史可見性，被邀請但還沒加入的人也可能該拿到房間金鑰，成員清單要不要含他們、帶不帶版本號。
6. **(B) 的 `CryptoState` 瘦身**：「別人的裝置清單變動」那一半對客製 client 變成不需要；「我自己的一次性金鑰數量」留著。
7. ~~**送出時把關**~~ ✅ 要，形狀是房間版本號（§7 第 6–7 條）。原題（問題書 #69）：有了成員版本號之後，送出時要不要帶「我依據的版本」讓 server 擋，還是只靠點進房間時的比對。
8. **聯邦**：遠端使用者換裝置要等對方通知到了才會反映在版本號上，保證只到「server 知道的」為止。

## 9. 目前的設計結論（草稿，細節文件的骨架）

### 9.1 server 要新增的

| # | 功能 | 內容 | 定了多少 |
|---|---|---|---|
| **F1** | **每個帳號的裝置版本號** | `mark_device_key_update` 這一個入口（五條路徑都經過）讓它變；一人一列、覆寫，不記歷史 | ✅ 要有、哪些變動算、`序號-雜湊` 變動鏈、雜湊內容（§7 第 2–4、8 條） |
| **F2** | **成員清單帶版本號** | client 點進房間（與送出前）拿到「這房的成員＋每人的版本號」，跟自己快取的比，不一樣的就重查 | ✅ 要有（§7 第 1 條），**加帶房間版本號**（§7 第 6 條）。被邀請的人不含（§7 第 10 條）。⏳ 從哪條路給（§8.4） |
| **F3** | **裝置變動廣播到帳號所在的每個房間**（擴展） | 短暫的房間訊號，記憶體扇出給正連著、且在 `Hello.features` 宣告過的訂閱者 | ✅ 採用（§9.2）。順手讓那些房間的房間版本號快取失效、帶上新的房間版本號（§9.5 第 1 條）。⏳ wire 上的 subtype 與排序 |
| **F4** | **送出時比對房間版本號** | 加密訊息帶房間版本號，對不上回 `1506 RoomDevicesChanged`，client 自動重試；沒有約定的不擋 | ✅ 採用（§7 第 6–7 條）。⏳ §9.5 的補強 |

### 9.2 還差一個決定：房間開著的時候，有人換裝置怎麼辦

F1、F2 解決「點進房間時」。但 Alice 開著房間的這段時間裡 Bob 換了裝置，Alice 下一則訊息送出前怎麼知道？三個選項，決定 server 是兩個還是三個新功能：

| 選項 | 怎麼做 | 正確性 | 代價 |
|---|---|---|---|
| **(i) 每次送出前都重拿 F2** | 不加功能 | 正確 | 大房間每則訊息都拿一整份成員清單，重 |
| **(ii) F3：版本號變動的即時通知** | Bob 的版本號一變，在**記憶體裡**推給 Bob 在的房間的訂閱者：「Bob 的版本變成 X」。不寫庫、不扇出到儲存 | **推掛了就漏**（靠 `gap` 補） | 幾乎零 |
| **(iii) F3＋F4：再加送出時把關** | 送出時帶「我依據的版本」，server 發現有成員的版本更新就拒收（問題書 #69） | **推掛了也不會靜默送錯** | 送出路徑多一個檢查 |

✅ **維護者 2026-09-17：F3 採用**，形狀是維護者提的「**把裝置變動廣播到這個帳號所在的每個房間**」—— 對 client 來說，它就像一種成員變動（「有新裝置加入」），走同一套處理邏輯：這個人的裝置過期了，下次發之前重查。

**F3 的形狀（草稿）**：

- **短暫的房間訊號，不是時間線上的事件**：只在記憶體裡扇出給那些房間**正連著的訂閱者**，不寫資料庫、不進歷史、不走聯邦、不需要任何人的權限（像「正在輸入…」那樣）。成本是「Bob 的房間數 × 那些房間正在線上的人」，而且只在 Bob 真的有變動時發生。
- **帶新的版本號**：client 只保留比較大的那個，推送的先後亂了也沒關係。
- **沒收到的補法**：房間沒開或人離線 → 下次點進房間的 F2；推送因佇列滿被丟 → `gap` 提醒重拿；最後一道 → F4 送出時把關，最壞被擋一次。
- 🚨 **它是擴展，看不懂的 client 必須不受影響**（維護者 2026-09-17 指定）。兩層保證：
  1. **只推給宣告過的連線**：client 在 `Hello` 的 `features` 裡宣告它看得懂這個訊號，server 才推。沒宣告的連線永遠收不到，**舊 client 連一個陌生的 pack 都看不到**。📎 這會是 server 第一次讀 client 的 `features`（wire-format §3.2 目前寫著「client 的 `features` server 目前不讀」），要一起改那一格。
  2. **名字帶命名空間**：訊號的類型用自訂前綴（例：`org.wbftw.device_version`），不佔 Matrix 的 `m.` 名字；萬一有 client 宣告了卻處理不了某個欄位，照 Matrix 的慣例忽略不認得的類型與欄位。
- ⏳ 細節文件要定：它是 `0x14 Event` 底下一個新的 server → client subtype，還是併進現有推送的某個位置（⚠️ 不能塞進 `Push` 的 data：那裡每一則都帶 `g_seq`、推進水位，混進沒有 `g_seq` 的東西會弄壞 client 的水位）；它帶不帶一個位置號讓 client 排序。

**考慮過、不做：把裝置變動寫成時間線上的真事件**（例：替 Bob 送一則狀態事件進他的每個房間）。現成的推送、補窗、排序都能用，但：
- **權限過不了**：狀態事件預設要權限 50，Bob 是一般成員會被房間授權規則擋；改成一般訊息類事件則會計入未讀、觸發通知、留在歷史裡。
- **以 Bob 的名義寫**：server 在 Bob 不知情時用他的名字往每個房間寫東西。
- **比上游的逐房變動列更重的扇出**：Bob 在 100 個房間，換一台裝置就是 100 則 PDU，每則都要簽章、雜湊、進 DAG、參與狀態計算。
- **外流與擠壓**：開聯邦就會同步出去；永久留在歷史裡；`Recent` 一窗被它佔位。

✅ **維護者 2026-09-17：選 (iii)，但 F4 改成比對「房間版本號」**（§7 第 6–7 條）。跟上表的 (iii) 差在：client 不必帶「我看過的每個成員的版本」（大房間很重），只帶一個號碼。補強見 §9.5。

### 9.3 不動、沿用的

- 成員變動：房間事件的推送與 `Recent` 補窗。
- 查金鑰、拿一次性金鑰、發 to-device：(A) 已經走橋。
- 自己的一次性金鑰數量：(B) `CryptoState` 的那一半。
- HTTP 那條：維持 Matrix 的 `device_lists`，給一般 client。

### 9.4 client 要做的

- 發房間金鑰用 `IdentityBasedStrategy`。
- 兩張表：全域的 1:1 通道保留；房間表在有人退房時清掉他，**並換一把新的房間金鑰**（SDK 的 `share_room_key` 在成員名單少人時會自己換）。
- 點進房間時拿 F2，版本號不一樣的人重查金鑰，當成 `device_lists.changed` 餵進 SDK。

### 9.5 房間版本號的補強（✅ 維護者 2026-09-17 同意，第 4 條改寫）

1. **放記憶體，不存資料庫**。它跟 §2 否決的「每房存一個版本號」不一樣的地方，是**隨時可以重算**：
   - 失效：房間有成員事件時；房裡有人的 F1 版本號變時 —— 後者就是 F3 已經在走的扇出，**不多一條路**。
   - 快取沒命中就當場重算；重啟、失效都不怕，沒有 migration、不會漂移。
2. **算法固定、client 算得出同一個值**：~~成員按帳號排序串成 `(帳號, 版本號)` 後取雜湊~~ → 維護者改成**全域位置、不用雜湊**，公式見 §7「第 8–10 條展開」。client 拿自己的成員事件 `g_seq` 與成員的位置取最大值，就能核對。
3. **有約定的 client 漏帶號碼要擋**：「沒帶就不擋」不加條件的話，客製 client 哪天漏帶一次就**靜默繞過**。綁在 `Hello.features`：沒宣告的連線不檢查；**宣告過的連線，加密訊息必須帶，漏帶回 `InvalidRequest`**。「只擋有約定的」仍成立，約定本身有強制力。
4. **重試是 client 的事，server 不規定**：server 只負責對不上就回 `1506`、帶上目前的 `room_version`；要不要重試、重試幾次，是 client 自己的政策。（維護者：「自動重試 1 次就夠了，而且這是 client 端的事」。草稿原本寫「最多 3 次」，那是替 client 定了政策，不屬於 server 的設計。）
5. **剩下的競態要寫明**：成員變動跟送出在同一把房間鎖底下，檢查精準；**換裝置（`mark_device_key_update`）不在房間鎖底下**，「Bob 在檢查完之後幾毫秒加了裝置」這個窗口關不掉。它比 Matrix 原本「查金鑰到送出」的窗口小很多，而且 F3 會在幾毫秒後通知；是可接受的剩餘風險，但要寫進細節文件。
