## 0. 起點

維護者 2026-09-16 的思路：

1. **Matrix 只規定結果，不規定怎麼算**，規格沒有保證任何實作的效率。
2. 現在「誰跟誰有共同加密房」這套底層，維護者不滿意，想從底層換掉。
3. **兩條路**：HTTP 照 Matrix 那套（給一般 client）；WS 是維護者自己的 client 專用，可以走特規，**讓 server 減重**。前提是結果正確。

## 1. 結論先講

- **只有「發」需要知道別人有哪些裝置**；「收」不需要（§3）。
- **成員變動不需要任何新東西**：它就是房間事件，已經被記錄、被廣播、有補窗（§4）。
- **server 唯一非給不可的是「某人的裝置變了」**，而且上游已經有這份紀錄（§5）。
- 成員、交集、`left`、每房發給過誰、何時換房間金鑰 —— **全部可以在 client 本地做**（§6）。
- ✅ **維護者 2026-09-17 定案兩條**（§7）：成員清單帶每個成員的版本號；裝置變動時帳號的版本號必須變。

## 2. 走過的路（考慮過、不做，理由留著）

| 想法 | 為什麼不做 |
|---|---|
| **成對表**：`(A, B) → 共有幾個加密房` | 「A、B 有共同加密房」是使用者與房間這張二分圖上的「距離 2」，成對表等於把圖平方後存起來：一個 1000 人房間是 50 萬條關係，有人進出就改一大片。**存一個推得出來的東西，代價卻是平方級。** |
| **只含加密房的成員索引** | 讓交集變短，但仍是在回答一個「不必問」的問題（§6）。 |
| **每個加密房存一個裝置版本號** | 那是把推得出來的東西又快取一次：要維護、要 migration、要重建指令，而且會跟事實對不上。 |
| **把成員變動也寫進逐房的變動列** | 那是**寫入時扇出**：一個事實寫 N 份（N 是他的房間數），寫了就永遠躺著。上游的金鑰變動就是這樣做的（`mark_device_key_update` 對每個房間寫一列），我們不該照抄到成員變動上。 |
| **全域的變動日誌**（一次變動一列，讀的人自己過濾） | 比扇出輕，但成員變動本來就在房間事件裡，根本不需要日誌；裝置變動則上游已經有每人的紀錄（§5）。多一條日誌就是多一個會長大的東西。 |
| **server 持續替每個 client 追蹤** | 那是 Matrix `/sync` 的選擇，不是 E2EE 的必要條件（§3）。 |

⭐ 這幾條的共同錯誤：**被 Matrix 的訊號形狀帶著走**。`device_lists.changed` 是「一串使用者」，於是底層一路被逼去回答「誰跟誰同房」；問題本身並不需要那個答案。

## 3. 收與發不對稱

| | 需要知道別人有哪些裝置嗎？ | 需要什麼 |
|---|---|---|
| **收**（解開別人的訊息） | **不需要** | 對方把那一輪的房間金鑰發給了**我這台裝置**：來源是我自己的 to-device 佇列、金鑰備份、或向我自己的其他裝置要。全是「我自己的東西」。 |
| **發**（我送加密訊息） | **需要** | 送出前，這一輪的房間金鑰必須已經發給房裡每個人的每台裝置。 |

📎 收的一邊唯一碰到別人裝置的，是顯示「這則訊息來自已驗證的裝置嗎」—— 看到陌生裝置時再查、查完快取，是顯示用的，不是解密用的。

**所以追蹤裝置只在兩個時機有意義**：

| 時機 | client 做什麼 | 碰到別人的裝置嗎 |
|---|---|---|
| 啟動、補歷史 | 拉自己的 to-device 佇列（收金鑰），需要時從備份補 | **不碰** |
| **點進房間（前景）** | **先問一次：這房有沒有人換過裝置、要不要重抓**；順便把房間金鑰發到位（暖機） | 只碰這個房間 |
| **按下送出** | 確認這房的成員與裝置是最新的，不是就補發，再送 | 只碰這個房間 |
| 關掉房間 | 不做事 | 不碰 |

另一種「發」是被動的：我自己的新裝置來要舊訊息的金鑰（`m.room_key_request`），只需要知道**我自己的**裝置清單。

**離線時追蹤別人的裝置沒有任何用處**；server 不必替任何人持續追蹤任何東西。

## 4. 成員變動：已經有了

`m.room.member` 是房間事件。`append_pdu` 把**每一個**新事件推給房間的訂閱者（`service/rooms/timeline/append.rs` 的推送），所以成員變動已經：

- **被記錄**：房間時間線上的一則 PDU，帶 `g_seq`（全域）與 `r_seq`（每房）。
- **被廣播**：房間的訂閱者立刻收到。
- **有補窗**：斷線重連用 `Recent`＋`gap`。

跟著房間走的 client，收到成員事件的那一刻就知道「這房的人變了」，不需要 server 再用別的頻道說一次。房間的水位（`r_seq`／`g_seq`）**完全適用於成員變動**。

## 5. 裝置變動：唯一要 server 提供的

「某人換了裝置」**不是房間事件**，不在任何房間的時間線上，房間水位看不到它，client 本地也推不出來。這是唯一轉嫁不到 client 的東西。

現在資料庫裡已經有的：

| 東西 | 存在？ | 形狀 |
|---|---|---|
| 當前的金鑰（每人每台裝置、交叉簽章金鑰） | ✅ | `keyid_key` |
| **每個人的金鑰變動紀錄** | ✅ | `keychangeid_userid` 以 `(使用者, 位置)` 為鍵，`keys_changed` 讀的就是它 |
| 每個房間的金鑰變動副本 | ✅ | **同一張表**另以 `(房間, 位置)` 為鍵 —— 逐房扇出。還有別的讀者：`/sync` 與聯邦（`sending/sender.rs` 組 `m.device_list_update` 時逐房掃它），所以**不能刪，只是通道不碰它** |
| 每人一個版本計數器 | 🤔 半個 | `userid_devicelistversion` 存在，但只有刪裝置那條路會遞增 |

- 號碼：金鑰變動的位置取自 `globals.next_count()`，**跟 `g_seq`、`cd_seq` 同一個計數器**，可以比先後；但它不是事件，傳遞跟房間事件分開。
- ⚠️ 計數器是兩階段的：位置順序 ≠ 看得到的順序（500 可能比 501 晚寫完）。任何「我看到位置 P 了」都要定義成「server 已提交到 P」，不是「我收到的最大號碼」—— (B) 實作 `dl_seq` 時踩過。

## 6. client 本地的兩張表

**全域表：跟哪些 (帳號, 裝置) 建過 1:1 通道**

- **保留，不因為沒有房間交集就刪**。1:1 通道（Olm session）不授予任何讀取權，只是「能加密傳東西給這台裝置」的管線；之後再同房、驗證裝置、轉發金鑰都用得上，不必再搶對方的一次性金鑰。
- 要修剪就依「多久沒用」，不依「有沒有交集」。

**房間表：這一輪的房間金鑰已經發給哪些裝置**

- 某人（例：`weil`）退房 → 從這個房間的表清掉他所有裝置；全域表不動。
- 🚨 **光清表不夠，一定要換一把新的房間金鑰。** Megolm 的房間金鑰可以往前推：weil 手上已有現在這一把，只要不換，他就算不在名單上也解得開之後用同一把加密的訊息。**清表是「不再發給他」，換金鑰才是「他讀不到之後的」。**

**跟傳統 client 的差別**：`matrix-sdk-crypto`（client repo 的 `vendor/`）內部**已經有這兩張表**：

| 這份的設計 | SDK 內部 |
|---|---|
| 全域：建過通道的裝置 | 裝置清單與 Olm session 永久存在本地 |
| 房間：發過金鑰給哪些裝置 | 每個房間的發送金鑰帶一份 `shared_with_set` |
| 有人退房就換金鑰 | `share_room_key(room, users, …)` 的**成員名單是 client 傳進去的**；名單少了誰就自動換鑰（`share_strategy.rs` 註解：「1. Any user left the room」） |

**真正的差別只有一個：誰告訴 client「某人的裝置過期了」。** 傳統是 server 持續算 `device_lists` 推給它（client 維護全域的「追蹤中的人」）；這裡是**點進房間或送出時，只問這個房間的成員**。

接 SDK 的方法：server 回的「換過裝置的人」當成 `device_lists.changed` 餵進去；第一次出現的成員用 `update_tracked_users` 登記。

## 7. ✅ 維護者 2026-09-17 定案

> **1. 提供成員清單時，必須包括每個成員的版本號**（代表他的裝置有沒有變動）。
> **2. 裝置變動時，帳號本身的版本號必須變。** 形狀可以是「序號＋所有裝置 ID 清單的雜湊」，例：`2-abcdef1234`。

這兩條合起來的效果：client 手上有「我上次看到的每個成員的版本號」，點進房間時拿成員清單一比，**不一樣的就是要重抓的人**；server 不必替 client 算任何交集或差異。

## 8. 下一份細節文件要回答的

1. **版本號的「序號」**：每人自己的小計數器（例中的 `2`），還是全域位置（跟 `g_seq` 同空間、可比先後）？`userid_devicelistversion` 現在只在刪裝置時遞增，要補到每一條裝置變動路徑上。
2. **「裝置變動」的範圍**：只有裝置 ID 清單變（新增、刪除）才算，還是同一台裝置**換了金鑰**、**交叉簽章金鑰換了**也算？⚠️ 後兩者裝置 ID 清單不變，**雜湊不會變**；若也要算，得靠序號部分來反映。
3. **雜湊**：用什麼演算法、取幾個字元、清單怎麼排序後再算；它存在的目的是讓 client 能拿本地的裝置清單自己算一遍比對嗎？
4. **成員清單從哪條路給**：橋的 `0x13 0x29 Members` 回的是 Matrix 原樣的 body，加欄位就改到 HTTP 的回應了。要另開原生的 pack，還是在推送的成員事件 `unsigned` 裡帶版本號？
5. **被邀請的人**：依房間的歷史可見性，被邀請但還沒加入的人也可能該拿到房間金鑰，成員清單要不要含他們、帶不帶版本號。
6. **(B) 的 `CryptoState` 瘦身**：「別人的裝置清單變動」那一半對客製 client 變成不需要；「我自己的一次性金鑰數量」留著。
7. **送出時把關**（問題書 #69）：有了成員版本號之後，送出時要不要帶「我依據的版本」讓 server 擋，還是只靠點進房間時的比對。
8. **聯邦**：遠端使用者換裝置要等對方通知到了才會反映在版本號上，保證只到「server 知道的」為止。
