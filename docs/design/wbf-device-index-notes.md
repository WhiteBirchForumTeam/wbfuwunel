## 0. 這份在記什麼

維護者 2026-09-16 的思路，原話的意思是三件事：

1. **Matrix 只規定結果，不規定怎麼算。** 規格沒有保證任何實作的效率，所以我們沒有義務照它暗示的做法做。
2. **現在「判斷兩個人有沒有共同加密房」的底層，維護者不滿意，想從底層換掉。**
3. **上面分兩條路**：WS 走特規的通知，HTTP 維持 Matrix 那套語意；**底下是同一個新的底層**，兩條路算出來的結果要一致。

⭐ 這個切法的重點：**特規的是通知的形狀，不是事實。** 事實（誰能解開這個房間的訊息）在 server 裡只有一份。

## 1. 現在的底層，成本在哪

判斷「A 跟 B 有沒有共同的加密房」＝ 兩個人的**全部**已加入房間求交集 → 對交集裡每個房間問「這房加密嗎」（`sync/mod.rs` 的 `share_encrypted_room`，(B) 之後搬到 `users/device_lists.rs` 的 `shares_encrypted_room`）。

- 每問一次都重算，答案不留下。
- ⚠️ **真正的成本不是這個函式，是呼叫它的次數**：一個 1000 人的房間有人加入，要對房裡每個人問一次；補窗要對我每個房間的每個成員問一次。
- 問題的形狀也繞：我們真正想知道的是「**這個房間的裝置集合變了沒**」，卻要翻譯成「**哪些使用者跟我還有共同加密房**」—— 那是 Matrix 把訊號掛在「使用者」身上造成的。

## 2. 底層的候選形狀（都還沒定）

分三層，越底下越不常變：

| 層 | 是什麼 | 維護點 | 現況 |
|---|---|---|---|
| ① **加密房的成員索引** | `使用者 → 他在的加密房`、`加密房 → 成員`，只含加密房 | 加入、離開、**房間被設成加密**（要把當下成員補進去） | 建議先做這層：交集的兩個清單短很多，而且省掉「逐房問是不是加密」那些查詢 |
| ② **房間的裝置版本 `dv`** | 每個加密房一個數字，成員或裝置變動就往前跳 | 同上 ＋ 金鑰變動 | 兩條路共用的事實；也是送出把關要用的（問題書 §4） |
| ③ **成對計數** | `(A, B) → 共有幾個加密房`，查一次就知道 | 每次成員變動要更新這個房間裡所有配對 | **建議先不做**：一個 1000 人房間變成加密房要寫 100 萬筆。列成候選，等量過真的還慢再說 |

## 3. 上面兩條路

| | HTTP（`/sync`、`/keys/changes`） | WS（特規） |
|---|---|---|
| 訊號掛在誰身上 | 使用者：`device_lists.changed`／`left` | **房間**：「房間 R 的裝置集合到版本 N 了」 |
| 怎麼算 | 從 ① 算出使用者清單，語意照 Matrix | 直接用 ② 的 `dv` |
| 推給誰 | 不推，client 自己拉 | **房間的訂閱者** —— 通道本來就有這份名單 |
| 成本 | 跟現在一樣或更低 | 幾乎零：不必求交集，也不必判斷誰跟誰同房 |

⭐ **房間層的通知在我們的通道上幾乎免費**：收件人名單就是 `Event/Push` 每天在用的房間訂閱者登記表（`service/streams/rooms.rs`）。訊號從「使用者」換成「房間」之後，「誰跟誰同房」這件事在 WS 這條路上**不是變快，是不需要**。

client 那邊不吃虧：它本來就知道每個房間有誰，所以「房間 R 變了」對它等價於「重查這幾個人的金鑰」。

再加上送出時的把關（問題書 #69），通知漏掉最壞只是被拒一次、重查、重送，**不會靜默送出別人解不開的訊息**。

## 4. 兩條路怎麼保證結果一致

- **同一份底層**：HTTP 那條算使用者清單時，讀的是同一份索引，不是另寫一套判斷（原則：同一個問題不要有兩份實作）。
- **e2e 逐位置比對**：這個守衛在 (B) 已經建好（e2e15 [1.8]：同一個位置比 WS 的補窗與 `/sync` 的 `device_lists`）。底層換掉之後，它就是「兩條路沒漂移」的紅綠燈。
- **索引要能重建**：既有資料庫沒有這份索引，需要啟動時建一次；另外要有「重建索引」的 admin 指令 —— 索引壞掉的症狀是靜默的。

## 5. 還沒決定的（下一份文件要回答）

1. **③ 成對計數**現在做，還是列候選？（暫時的看法：列候選）
2. **WS 的通知形狀**：房間層的 `dv`，還是保留使用者清單、只是底層變快？
3. **HTTP 送加密訊息**：特規的把關只在通道上，HTTP 就是繞過的入口。要嘛加密房只能走通道送（**這是破壞 Matrix 相容，要點名等維護者同意**），要嘛明講 HTTP 不保證。
4. **`CryptoState` 要不要跟著瘦身**：改成房間層之後，它可以縮成「我自己的金鑰存量」＋「哪些房間的版本變了」。
5. **聯邦**：遠端使用者換裝置要等對方的 `m.device_list_update` 到了 server 才知道，保證只到「server 知道的」為止。
