## 1. 目標

做一套**自架、可完全掌控的即時通訊服務**，體驗對標 Telegram。

「可掌控」具體指三件事：

1. 資料存在哪、留多久、誰讀得到，由維護者決定，不由協定的歷史包袱決定。
2. 容量是**有界**的 —— 刪掉的東西真的會消失，儲存量算得出來。
3. 大檔案與串流是**一等公民**，不是繞路兜出來的。

### 明確的非目標

| 不做 | 理由 |
|---|---|
| **聯邦（federation）** | 它是 Matrix 九成複雜度的來源，而維護者的使用情境裡沒有第二個組織 |
| **server 端媒體轉檔 / 內容過濾** | E2EE 下 server 只看得到密文，這在原理上做不到（見 §5.4） |
| **與 Matrix 規格相容** | 一旦要相容，下面每一個改進都得走 MSC 流程，等於放棄自主性 |

## 2. Matrix 敗在哪三件事

這三點是選型時實際遇到的不滿，按嚴重程度排序。

### 2.1 大檔案：沒有續傳

Matrix 的媒體上傳是**一個單發 HTTP POST**，沒有 range、沒有分塊、沒有續傳。

10 GB 傳到 97% 斷線 = 從零開始。這對「拿來當主力檔案傳輸管道」是致命的。

### 2.2 沒有串流

- **媒體流**：下載沒有可驗證的 range request，所以影片不能邊下邊播、不能跳轉。
- **文字流**：事件是不可變的，串流文字只能用 `m.replace` 關聯模擬 —— 每更新一次就發一個完整的新事件說「這個取代那個」。把 LLM 的 token 串流餵進去特別難看。

### 2.3 儲存只長不縮，刪除沒有語意

**協定層不存在媒體刪除。** C-S API 裡沒有這個端點。使用者能做的最強動作是 `m.room.redaction`，而 redaction 是**對事件**做的 —— 它把事件內容剝空，但媒體儲存那邊完全不知道發生過這件事。

後果（全部是實際會發生的）：

- 雙方都刪訊息、都退出房間 → 檔案 bytes 一個位元組都沒少。
- `purge history` 清掉房間歷史 → 事件沒了，**檔案還在**。
- 遠端 server 快取過的副本，來源端刪不到，也**查不出來有幾份**（聯邦協定裡沒有「刪除媒體」這種交易類型）。
- 事件本身也永遠留著：redact 之後節點還在，只是變成剝空的墓碑 —— 因為後面的事件用 `prev_events` / `auth_events` 指著它。

能真的刪 bytes 的手段全部是 operator 層、帶外、時間驅動的（admin API 按 ID 或日期刪、`media_retention` 到期、外掛的 state group 壓縮工具）。**保留是預設，清理是例外。**

## 3. 根因：一個架構決定推出來的全部後果

這三件事**不是三個獨立的缺陷，是同一個決定的三個後果**。理解這點才知道哪些能修、哪些是命。

Matrix 的核心是：**房間 = 一張不可變、已簽章、複製到每台參與 server 的事件 DAG。**

- **不可變 + 已簽章** → 沒辦法簽一個還沒寫完的東西 → **串流在結構上被排除**。
- **複製到每台 server** → 事件必須小（規格上限 65536 bytes，算的是整個 PDU）→ **大內容不可能進事件**。
- **節點不能消失** → 後續事件指著它 → **事件層的真刪除在結構上不可能**。

於是媒體 bytes 被**刻意推出 DAG 之外**（`mxc://` 只是一個指標）。這個決定本身是對的 —— 沒有人想要 10 GB 複製到每台 homeserver。

**但代價是媒體從此變成「掛在旁邊的另一個東西」，而它拿到的是最低限度的 API：POST 上傳、GET 下載，結束。**

證據：它到很近期才補上認證（在那之前媒體 URL 形同公開）。一個連 auth 都是後來補的子系統，當然不會有續傳、range、引用計數。

### 3.1 關鍵區分：哪些是命，哪些只是沒做

這一節是整份文件裡最重要的判斷：

| | 性質 | 我們能不能贏 |
|---|---|---|
| **事件層不能真刪** | **結構性**。選了可驗證的複製 DAG 就等於選了節點不可消失 | 能 —— 但代價是放棄 DAG（見 §7 待驗 6） |
| **事件層不能串流** | **結構性**。不可變 + 簽章 | 能 —— 走旁路，不進不可變日誌（見 §5.3） |
| **媒體不能續傳 / seek / 刪除** | **只是沒做**。媒體根本不在 DAG 裡，沒有任何結構性理由 | **能，而且乾淨** |

**媒體那一半是純粹的實作缺口，不是取捨。** 這是投入報酬率最高的地方。

### 3.2 順帶一提：這也是 Telegram 的取捨的另一面

Telegram 能串流、轉檔、縮圖、CDN range，是因為**cloud chat 根本沒有端對端加密**（只有 Secret Chat 有），伺服器手上是明文。它能做 delete-for-everyone，是因為只有一個權威、沒有複製的簽章圖。

**Telegram 的串流媒體與 Matrix 的預設 E2EE，是同一個取捨的兩面。** 要兩個都要，就得正面解「在密文上做可驗證的 range request」—— 那正是 §5 的內容。

## 4. 核心洞察

> **續傳、串流播放、真正的刪除 —— 這三件事共用同一個資料結構。**

那個結構是：**內容分塊 + Merkle 樹 + 引用計數**。

這代表它們不是三個各自要押注的功能，而是**一個設計決定的三個後果**。做對這一層，三個一起拿到。

## 5. 設計草案

### 5.1 為什麼 Matrix 的密文 seek 不了 —— 卡點非常具體

先講清楚卡在哪，因為這決定了要改什麼。

Matrix 的加密附件用 **AES-256-CTR**（實測確認：`mautrix.crypto.attachments.decrypt_attachment(ciphertext, key, sha256, iv)`）。事件裡帶的 `EncryptedFile` 大致長這樣：

```
url:    mxc://...
key:    { k: <base64url AES-256 金鑰>, alg: "A256CTR", ... }
iv:     <base64，8 bytes nonce + counter>
hashes: { sha256: <整份密文的雜湊> }
```

關鍵事實兩條：

1. **CTR 模式天生可以 seek。** keystream 的第 i 塊是 `E(K, nonce ‖ counter+i)`，只跟 counter 有關。要解 byte range `[/docs/design/build/windows-build.md](../build/windows-build.md)。

3. **塊大小。** 10 GB 檔案下：1 MiB → 10240 塊、樹深約 14、證明約 448 bytes；4 MiB → 2560 塊、樹深約 12。兩者都可行，要拿實際的網路狀況與記憶體佔用去量。

4. **串流文字在 E2EE 下的金鑰安排。** 每個短暫訊框各自加密的成本？還是一條串流開一個短期 session？

5. **引用計數的寬限期與「復原」語意。** 使用者刪了又想救回來，窗口多長？窗口內 bytes 還在，這件事要不要對使用者明說？

6. **客戶端策略。** 自己全寫，還是站在現成的 Rust SDK 上。
   ⚠️ **這一項原本附帶一句「順帶解掉 Windows 沒有 C 加密函式庫原生建置路徑的問題」，那句話是錯的，已刪除。**
   `aws-lc-sys` 在 Windows x86_64 有正規建置路徑（CMake ＋ NASM），2026-09-01 的建置就是走它過的。
   所以**「Windows 建置」不再是選客戶端策略的理由**，這一題要純粹按客戶端本身的取捨來決定。

## 8. 附錄：這份文件裡哪些是查證過的

⭐ 誠實標註涵蓋範圍，免得下一個讀的人把判斷當事實。

**實際在程式碼裡看過（2026-09-01，hermes-agent repo）**

- 加密附件解密的呼叫形狀 `decrypt_attachment(bytes, key, sha256, iv)` → 確認是 **AES-CTR + 整份密文一個 SHA-256**。這是 §5.1 那個卡點的直接證據。
- 事件大小規格上限 65536 bytes 算的是整個 PDU。

**實際跑過（2026-09-01，這個 repo）**

- Windows 建置與啟動 —— 見 §7 待驗 2 與 [/docs/design/build/windows-build.md](../build/windows-build.md)。不是只看編譯綠燈：
  RocksDB 實際開起來、HTTP 端點實際回應過。
- 這份文件對程式碼結構的假設，整理在 [/docs/design/overview/repo-structure.md](repo-structure.md)。

**規格 / 生態系知識，未在本次逐條查證**

- 媒體儲存沒有一般使用者可用的刪除端點；`purge history` 不連帶刪媒體。
- 遠端 server 的媒體快取按各自的過期設定活著，且聯邦協定沒有「刪除媒體」的交易類型。
- 狀態群組的成長問題嚴重到社群需要外掛壓縮工具。
- 訊息保留策略的相關提案仍是草案 / 實驗性質。

**純粹是判斷，不是事實**

- 「Matrix 上游會補媒體那塊，但是以年計，而且形狀多半跟我們要的不一樣」。
  依據是**顯露偏好**：媒體子系統冷了十年，唯一一次認真動它是被安全問題（媒體 URL 形同公開）逼的，不是能力缺口；而近幾年的力氣都在同步效能、客戶端、下一代認證上。
- 因此**時機風險不在媒體**（沒人碰的子系統不會在腳下移動），而在同步傳輸與認證那兩塊正在遷移的地方。
