# 媒體被刪得太早的兩條路

來源是外部審查點出的兩條（安全性第三條、bug 第一條）；2026-11-04 對著程式與既有設計文件
逐條驗過，下面寫的是**驗到的**，不是審查的敘述（轉述一條審查意見不等於確認它成立 ——
同一批審查裡的另一條就不成立）。

| | 狀態 |
|---|---|
| §2 洞 A：第三方「先持有再放掉」繞過保護期 | ✅ **維護者 2026-11-07 同意修法**（§2.4） |
| §3 洞 B：引用讀取器看不到巢狀位置 | 📄 **提案**，另一支，兩支都從 `main` 開 |

兩條都只會往一個方向壞 —— **bytes 被刪掉，而刪掉救不回來**。這跟
[/docs/design/media/purge-release-set.md](purge-release-set.md) §3 定的方向反過來：
「媒體留太久救得回來，媒體放太早救不回來」。

## 1. 這份文件回答什麼

**「什麼時候可以刪掉一份媒體的 bytes」只有一個決策函式**
（`src/service/media_refs/collect.rs` 的 `is_removable`：本站的、`mxc_managed` 有列的、
沒有任何持有者），而它有**兩個觸發**：

| 觸發 | 什麼時候 | 保護期（`media_unreferenced_grace_seconds`，≥ 7 天）有沒有看 |
|---|---|---|
| `collect(mxc)` | **某個持有者剛被拿掉**、那筆交易提交之後 | ❌ **沒有** |
| `sweep_unreferenced()` | 每 `media_gc_sweep_interval` 一次 | ✅ 有 —— 但寫在**候選過濾**（`created < protected_since`）裡，不在 `is_removable` 裡 |

⭐ 這就是 CLAUDE.md A4 講的那個形狀：**同一個問題有一份半的實作。**
保護期是政策，它住在兩個觸發之中的一個裡面，所以另一個不受它管 —— 而不受管的那個
是**外人碰得到**的那個（§2）。

📎 上面那張表是**修之前**的樣子。§2.4 定的做法是把觸發收成一個（只留掃描），
而不是讓兩個觸發共用一條政策。

## 2. 洞 A：第三方「先持有再放掉」就能刪掉別人還在保護期內的媒體

### 2.1 兩個請求就夠

前提：受害者 A 上傳了一份媒體（`mxc_managed` 有列、**還沒被任何東西指到**
—— 這正是保護期存在要保護的狀態），攻擊者 B 知道那個 mxc（最常見的來路：
A 在 E2EE 房裡把它貼出來，而 B 就在那個房裡）。

```
1) PUT /_matrix/client/v3/profile/@b:ours/avatar_url   { "avatar_url": "mxc://ours/A的那份" }
   → set_avatar_ref 加一個 Holder::Avatar{localpart:"b"} 持有者
2) PUT /_matrix/client/v3/profile/@b:ours/avatar_url   { "avatar_url": "mxc://ours/別的" }
   → 舊的那份被釋放 → hand_to_collector → collect("mxc://ours/A的那份")
   → is_removable：本站 ✅、managed ✅、沒有持有者 ✅  ⇒ 刪掉
```

A 的媒體在**上傳後幾秒**就能被別人刪掉，保護期一天都沒用上。

### 2.2 為什麼現有的防線都沒擋

這套模型**有**「上傳者是不是 sender」這條檢查 ——
[/docs/design/media/media-attachments.md](media-attachments.md) §4.2，用在**宣告的
`attachments`** 上，而且是 fail closed（不過就整則拒送）。

但加持有者的路**不只那一條**，另外兩條都沒有這個檢查：

| 加持有者的路 | 檢查上傳者嗎 |
|---|---|
| 宣告的 `attachments`（§4.2） | ✅ 要求上傳者 ＝ sender |
| 明文 `content` 掃到的（`list_content_mxc_uris`） | ❌ 沒有 |
| 頭像（`set_avatar_ref` / `set_room_avatar_ref`） | ❌ 沒有 —— `src/service/profile/mod.rs:396` 把 client 送來的字串原封不動交下去 |

⚠️ 而「加持有者沒有檢查」本身**不是**這個洞 —— 讓別人的媒體多一個持有者是**留得更久**，
方向是安全的那邊（轉傳別人的圖片本來就該讓那份活著）。
🚨 **洞在於「拿掉持有者」這個動作被接到了一個不看保護期的刪除決策上。**

### 2.3 既有文件的理由句，前提少了一個

[/docs/design/media/media-attachments.md](media-attachments.md) §4.3 寫：

> 為什麼不用區分「從沒被指」跟「被指過又歸零」：後者收集器當下就刪了，
> 能在 0 停留超過保護期的只有前者。

這句在**釋放者就是上傳者**的時候完全對。而它少了那個前提：**任何人都能把一份
「從沒被指」的媒體，變成一份「被指過又歸零」的媒體** —— 於是它就落進「收集器當下就刪了」
那一類。⭐ 這不是實作偏離文件，是文件自己的推理漏了一格，所以修的時候兩邊都要改。

### 2.4 修法（維護者 2026-11-07 定）：釋放只釋放，刪除只在掃描裡

> 「釋放 holder 只釋放，不刪。清不清理靠後台，後台會自動砍 > 7 天保護期。」

兩件事：

1. **收集器整個退場。** 拿掉持有者就只是拿掉持有者，不交給任何人、不當下刪。
   `hand_to_collector`、`collect()`、行程內的釋放佇列（`released`）與 `interrupt()`
   都不再需要，服務的 `worker` 只剩掃描的計時器與關機。
2. **`is_removable` 留著，而且保護期進到它裡面**：

```
is_removable(mxc) = 本站 && mxc_managed 有列 && 比保護期老 && 沒有任何持有者
```

#### 為什麼這樣比「兩個觸發共用一條政策」好

⭐ **它把不可逆的動作從最容易寫錯的那些路上拔下來。**
釋放的路有六七條（redact 留備份／不留備份、備份到期、`purge_original`、
`purge_history` 逐事件、刪房、兩種頭像交換），而
[/docs/design/media/media-holders.md](media-holders.md) §1 記的歷史就是這些路**反覆寫錯**：
引用計數時代「每個 ±1 必須恰好一次」，三支 PR 連續在補「誰負責這個 −1」，第三支還是被
審查抓到雙扣。

- **今天**：釋放路寫錯（多釋放一次、釋放了不該釋放的）＝ **媒體被刪掉**，救不回來。
- **改完**：同一個錯誤 ＝ 媒體早一點變成「沒人持有」，然後**掃描照保護期處理** ——
  最壞的結果是它比預期早幾天被清，而且在那之前每一次掃描都還會重新問一次。

🚨 **而這個修法成立的前提是「掃描本來就是完整集合」，這點驗過**：
`sweep_unreferenced` 走 `mxc_managed` 的整張表（`raw_stream()`），所以一份媒體**怎麼**
失去持有者都無關 —— 掃描都會找到它。收集器從來不是「唯一知道它該刪」的人，只是早一點動手。

#### 保護期的門檻只定義一次

⚠️ 掃描的候選過濾**不能**拿掉：它是唯一讓掃描不必把全部 managed 媒體收進一個 `Vec`
的東西。但它跟判準各算一次「現在 − 保護期」就是**同一條規則寫兩份**，所以門檻由一個
取用點給出，兩邊都讀它：

```
get_grace_cutoff_millis()      ← 「現在 − 保護期」只有這裡算
    ↑                     ↑
is_removable()        掃描的候選過濾（只是最佳化，語意由 is_removable 負責）
```

#### 代價，兩個

1. **刪除慢最多一個掃描間隔**（`media_gc_sweep_interval`，預設 3600 秒）。老過保護期的
   媒體被釋放之後，今天是當下刪，改完是「下一次掃描」。要更快就把間隔調小。
   📎 而在預設設定下這件事本來就不是「當下」：`save_unredacted_events` 預設 **true**、
   原文留 60 天，所以 redact 不會讓媒體空出來（`Event` 換成 `Backup`，
   [/docs/design/media/media-holders.md](media-holders.md) §3 的表）。
   config 自己的註解就是這樣寫的：「media goes when the last retained original is dropped,
   not when the message is redacted」。
2. **掃描變成唯一的刪除者** ⇒ 它沒跑就完全不刪，磁碟只會長。方向是安全的那邊
   （不刪＝不會丟東西），但它從兩條路變一條路，所以**那條路要看得見**：掃描跑完
   固定留一行（候選數、刪除數），而不是只在「有候選」時才說話 —— 不然「掃描其實早就
   死了」沒有人會發現。

### 2.5 測試：一支整合測試 ＋ 兩支 e2e 的改寫

`src/main/tests/media_release_does_not_delete.rs`（對真的 server 與真的資料庫跑）一支裡四件事：

1. **第三方 hold-then-release 刪不掉保護期內的媒體** —— 而且是用**公開 API** 走完
   §2.1 那兩個請求（`profile.set_avatar_url` 兩次，攻擊者從沒上傳過任何東西）。這條就是洞 A。
2. **兩個持有者釋放掉一個，媒體仍然被持有；釋放第二個才變成沒人持有。**
   ⚠️ 這條以前由 e2e9 `[1.3]`（同一個附件被兩則事件宣告、各 redact 一次）看得到，
   因為第二次釋放當場刪檔；**現在兩次釋放都不刪，client 看不出差別**，所以它只剩這裡釘著。
3. **老過保護期的照樣會被清**：把保護期用環境變數壓成 0 → 跑一次掃描 → 上面兩份都有墓碑。
   ⭐ 沒有這條，前兩條可以靠「什麼都不刪了」通過 —— 而那是這支最可能的壞法。
4. **同一次掃描裡，還有持有者的那份沒被碰** —— 不然第 3 條可以靠「掃描刪光一切」通過。

而 **e2e9 與 e2e10 原本有九條斷言寫的是「釋放當下就 410」**，那是舊契約。改寫的做法一樣：
每條原地改成「釋放了，但保護期內照樣送得出來（200）」，而**判別力搬到各情境結尾的一次
刻意掃描**（`WBFUWUNEL_MEDIA_GRACE_SECONDS=3` ＋ 重啟 ＋ 等一個 `media_gc_sweep_interval`），
在那裡一次斷言整個分割：被釋放的那幾份 410、仍然被持有的那幾份 200。
⭐ 這樣「掃描什麼都不刪」與「掃描刪光一切」都過不了，而且**沒有任何一條斷言在跟掃描賽跑** ——
每一份媒體在那次掃描之前，要嘛被持有、要嘛在保護期內。

📎 順帶修掉一條名字在說謊的斷言：e2e9 `[1.7b]` 叫「media referenced by a live event is
untouched by the sweep」，而它問的那份是 `[1.6]` 那個**沒有宣告**的上傳 —— 房間是加密的，
server 從來沒看到任何引用，所以**沒有任何東西持有它**；它活著是因為保護期。
（`[1.6]` 警告它的上傳者，講的就是同一件事。）

### 2.5b 跟著改的行為（client 看得到的）

1. 🔴 **redact 之後 bytes 不再當場消失。** 在 `save_unredacted_events = false` 的站上，
   redact 一則圖片訊息以前當下就刪檔；現在它要等保護期過完，再等一次掃描。
   📎 預設設定（`save_unredacted_events = true`，原文留 60 天）本來就不是當下刪，所以預設沒差。
2. ⭐ **剛剛被釋放的媒體可以再被宣告一次，而且那是對的。** 以前「redact → 媒體沒了 →
   再宣告它會被 §4.2 的墓碑檢查拒絕」；現在檔案還在，所以宣告成功，而且**成功的那一刻它又
   被持有了** —— 等於保護期內的轉傳／重送會把檔案救回來，不必重新上傳。
   📎 e2e9 原本的 `[1.5d]` 測的是前者，所以它搬到那次刻意掃描之後（真的有墓碑的時候），
   名字改成 `[1.9]`。
3. 📎 **掃描每次都會留一行 log**（以前只有「有候選」時才留）。運維上這是刻意的：
   掃描現在是唯一的刪除者，而一個死掉的掃描跟一個沒事可做的掃描，在 log 裡以前長得一樣。

### 2.6 留著不動的

- **墓碑原因 `TombstoneReason::GarbageCollected`** 留著只給舊墓碑解碼用，
  跟當年 `Migrated` 同一個處置（[/docs/design/media/media-attachments.md](media-attachments.md) §4.4）。
  改完之後掃描只會寫 `Unreferenced`。
- **每個 mxc 一把鎖**（`hold_media`）照舊：決策與刪除之間要排除「同時有人加持有者」，
  而這件事跟誰在做決策無關 —— 掃描一樣要持鎖。
- **admin 的刪除指令**不受影響：那是明示的指令，不走這條判準。
- 📎 掃描把候選**全部**收進一個 `Vec<String>` 再處理，這點這支不動（改成邊走邊處理會動到
  鎖的持有範圍）。它今天就是這樣，只是現在變成唯一的路 ⇒ 記成後續。

## 3. 洞 B：引用讀取器是四條平的路徑，巢狀的位置看不到

`src/core/matrix/media_ref.rs` 的 `MXC_CONTENT_PATHS` 是四條固定的鍵鏈：
`url`、`info.thumbnail_url`、`file.url`、`info.thumbnail_file.url`，
而它的註解自己寫「這張表就是『這個事件引用媒體』的全部定義」。

於是**沒寫在表上的位置＝沒有持有者＝ sweep 在保護期過後把它清掉**，而送訊息的人
不會收到任何訊息。漏掉的是這三類：

| 漏掉的位置 | 誰在用 | 為什麼表上寫不出來 |
|---|---|---|
| `m.new_content.url`（以及它的 `info.thumbnail_url` 等等） | 編輯（`m.replace`，Matrix 規格內） | 可以加四條 —— **這類加得出來** |
| `images.<shortcode>.url` | 自訂顏文字／貼圖包（MSC2545，`im.ponies.room_emotes` 這類 state 事件） | 中間那一格是**使用者定的鍵名**，固定鍵鏈表達不出來 |
| 陣列裡的每一項 | 相簿類的提案（MSC4274） | 表只能走物件的鍵，不能走索引 |

⚠️ **編輯那一類今天多半僥倖沒壞**：client 編輯圖片訊息時通常也會在**頂層**重複一份
`url`（頂層是 fallback），而頂層那條在表上。但規格沒有保證它一定在，
所以這是「碰巧」而不是「守住」。而顏文字包那一類**沒有僥倖可言**：
頂層完全沒有 `url`，七天後整包圖消失。

### 3.1 建議的修法：有界的樹走訪，正面認得鍵名

把「四條固定路徑」換成一條規則：

> **content 這棵樹裡，任何鍵名是 `url` 或以 `_url` 結尾、值是字串、而且以 `mxc://` 開頭的，
> 都算一個引用。**

- ✅ 現有四條全部落在這條規則裡（`url`、`thumbnail_url`、`file.url`、`thumbnail_file.url`），
  三類漏掉的也都落進來。
- 🚨 **這裡的 fail closed 是「寧可多認」，不是「寧可少認」。** 認出來＝多一個持有者＝
  媒體多活著；沒認出來＝沒有持有者＝**保護期過後被清掉**。所以鍵名規則要寬的那一邊，
  而不是嚴的那一邊 —— 跟平常「不確定就拒絕」的方向相反，因為這裡的「拒絕」是刪檔。
  📎 代價是別人可以在自己的訊息裡放一個 `url` 欄位讓你的媒體一直活著 ——
  那是「留太久」那一邊，而且 §2 的修法之後它也不再是一個刪除的把手。
- 🔴 **走訪要有界，而且不用遞迴**（CLAUDE.md P）：事件內容是攻擊者給的 JSON，
  遞迴走訪碰到幾千層嵌套會把 stack 爆掉，而 stack overflow 是**整支程式**一起收掉、
  不走任何我們寫的收攤路。⇒ 明確的 worklist ＋ 深度上限（8）＋ 節點數上限（1024），
  到上限就停下來，回已經認出來的那些（而不是回 `Err`、也不是 panic）。

### 3.2 已經存起來的事件不會回頭補

讀取器換了，**只對之後存進來的事件生效** —— 這件事它的註解本來就寫明了
（「加一個鍵要重建索引才會對已存的事件生效」）。所以舊的顏文字包仍然沒有持有者。

兩個先例在 repo 裡：`rebuild_relation_index`、`rebuild_thread_index`
（`src/admin/debug/`）。要不要照著加一支 `rebuild_media_ref_index`，我列成 §4 的問題 ——
它是**另一個**規模（要掃全部房間的全部事件），我不想把它偷渡進這支。

### 3.3 測試

1. 三類位置各一條：`m.new_content.url`、`images.<code>.url`、陣列裡的 `url`，都要被認出來。
2. **既有四條路徑的結果一個字都沒變**（含順序與去重）—— 這條防的是「換規則順手改了舊行為」。
3. **界**：深度 9 的嵌套、2000 個節點的 content，各一條 —— 要回得來，而且不 panic。
4. 不是 `mxc://` 的 `url`（`https://…`）、不是字串的 `url`（物件、數字）都不算。

## 4. 狀態與還沒定的

| | |
|---|---|
| 洞 A 的修法 | ✅ **維護者 2026-11-07 定**（§2.4）：釋放只釋放，保護期進 `is_removable`。收集器退場 |
| 兩個洞幾支 PR | ✅ **兩支**，都從 `main` 開（CLAUDE.md R 條，FORBID 疊）。洞 A 是這一支 |

真的要告警是運維那邊的事。
